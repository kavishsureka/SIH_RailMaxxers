# ML priority model deep dive

This document explains the implemented machine-learning pipeline under `ml/`, its runtime integration, its limitations, and how its output influences scheduling.

## 1. What the model does

RailBlock has one ML model: a scikit-learn `GradientBoostingRegressor` that predicts a continuous task priority score from 0 to 100.

The model does not predict:

- task duration;
- train delay;
- failure probability;
- maintenance need;
- feasibility;
- block start/end time;
- which task may be dropped.

Those responsibilities remain in data inputs, the C++ optimizer, and the independent validator. ML influences ordering and the cost of delaying high-priority work; it never overrides HARD train, availability, compatibility, dependency, critical due-date, or exactly-once constraints.

## 2. Honest model status

The committed `priority_gbr_v1.joblib` is a prototype policy surrogate. It is trained on deterministic synthetic features whose target labels are generated by a known bootstrap formula. Therefore its excellent held-out metrics measure how well Gradient Boosting reproduces that synthetic formula and distribution. They do not prove predictive performance on Indian Railways decisions or operational outcomes.

This distinction should be stated during demonstrations:

> The ML component operationalizes a replaceable priority interface and provenance pipeline. Version 1 learns a synthetic bootstrap policy for a reproducible prototype. A railway pilot would retrain and calibrate it using historical expert decisions and/or outcome labels.

## 4. Feature schema

`FEATURE_NAMES` fixes this exact order:

```text
severity
asset_criticality
overdue_factor
deadline_urgency
```

All four inputs are normalized to `[0,1]` by `extract_task_features`.

### 4.1 Severity

```text
severity_feature = clip(task.severity / 10)
```

### 4.2 Asset criticality

The extractor first looks for `asset_criticality`. If absent/empty—as in current scenario CSV—it falls back to the `criticality` column:

```text
criticality_feature = clip(criticality / 10)
```

### 4.3 Overdue factor

If an explicit `overdue_factor` is present, it is converted to float and clipped. Otherwise:

```text
overdue_factor = clip(max(0,-due_slot/2688))
```

Current generated scenarios have nonnegative due slots, so this fallback is always zero. The v1 runtime therefore receives no positive overdue signal from current scenario CSVs, although synthetic training includes overdue examples.

### 4.4 Deadline urgency

```text
deadline_urgency = clip(1 - max(0,due_slot)/2688)
```

Earlier due slots produce higher urgency. A due slot at or beyond the horizon produces zero urgency.

### 4.5 Matrix contract

`feature_matrix` builds `float64` NumPy rows in `FEATURE_NAMES` order and reshapes to `(number_of_tasks,4)`. Metadata feature names must exactly equal `FEATURE_NAMES` during inference; otherwise inference raises `ValueError`.

## 5. Synthetic training distribution

`generate_synthetic_data(sample_count,seed)` uses `numpy.random.default_rng` and produces non-uniform examples.

### Severity

Most values come from `Beta(2.2,3.4)`. A 12% critical tail is replaced with `Beta(8.0,1.8)`.

### Asset criticality

Criticality is correlated with severity but retains independent variation:

```text
clip(0.48 × severity + 0.52 × Beta(2.6,2.2))
```

### Overdue factor

About 18% of samples receive a nonzero `Beta(1.4,4.0)` overdue value. The remainder are exactly zero.

### Deadline urgency

Base urgency follows `Beta(2.0,2.8)`. A 10% urgent subset is replaced with `Beta(7.0,1.7)`.

The optional generator CLI can write these features and targets to CSV, but training regenerates them in memory from the configuration.

## 6. Bootstrap label policy

`ml/src/labels.py` defines:

```text
priority = 100 × (
    0.40 × severity
  + 0.20 × overdue_factor
  + 0.25 × asset_criticality
  + 0.15 × deadline_urgency
)
```

This function is not called during API inference. It exists only to generate offline synthetic targets. Separating it from `inference.py` prevents accidental runtime fallback to the old hand-written policy.

Because the target is a smooth deterministic weighted formula, held-out scores mainly test whether the model approximates that formula on the synthetic distribution.

## 7. Training configuration

`ml/config/model.json` currently specifies:

```json
{
  "model_version": "v1",
  "random_seed": 26027,
  "sample_count": 50000,
  "test_size": 0.2,
  "hyperparameters": {
    "n_estimators": 160,
    "learning_rate": 0.05,
    "max_depth": 3,
    "min_samples_leaf": 8,
    "loss": "squared_error",
    "random_state": 26027
  }
}
```

`train.py` uses `train_test_split` with the same random seed, yielding 40,000 training and 10,000 held-out examples. It fits `GradientBoostingRegressor`, clips held-out predictions to `[0,100]`, and calculates MAE, RMSE, and R².

The model is persisted with joblib. Metadata records model/type/version, training source, feature names, sample counts, random seed, metrics, full resolved hyperparameters, scikit-learn version, and UTC training timestamp.

## 8. Recorded v1 metrics

`ml/models/priority_gbr_v1.metadata.json` currently records:

| Metric | Value |
|---|---:|
| Held-out MAE | 0.4054213952 priority points |
| Held-out RMSE | 0.5447148274 priority points |
| Held-out R² | 0.9981972798 |

Interpretation: on held-out synthetic samples drawn from the same generator, predicted scores are typically within well under one point of the bootstrap formula. These are reproducibility/approximation metrics, not external-validation metrics.

## 9. Runtime inference

`ml/src/inference.py` is inference-only:

1. read selected `tasks.csv` with `csv.DictReader`;
2. load the joblib artifact;
3. load metadata JSON;
4. require metadata feature names to equal `FEATURE_NAMES`;
5. build the feature matrix;
6. call `model.predict` once for the complete batch;
7. clip predictions to `[0,100]`;
8. return model metadata and one prediction record per task.

Prediction JSON fields:

```json
{
  "task_id": "T001",
  "priority_score": 72.123456,
  "priority_source": "ML Prediction",
  "priority_model_version": "v1"
}
```

The Python CLI can also write `task_id,priority_score` CSV for C++.

## 10. Go integration

`backend/internal/optimizer/runner.go` owns the runtime orchestration.

`CommandRunner.infer` launches:

```text
ML_PYTHON -m ml.src.inference
  --tasks <selected-scenario>/tasks.csv
  --model ML_MODEL
  --metadata ML_MODEL_METADATA
```

Its working directory is `PROJECT_ROOT`, enabling the `ml` module import. It rejects process errors, invalid JSON, empty predictions, and missing model version.

`writePriorities` writes predictions to a temporary CSV with six decimal places. `CommandRunner.run` passes that same file to the C++ command. A benchmark launches one ML batch and then runs Independent, Greedy, and CP-SAT inside one C++ process, so the algorithms cannot receive different scores for that request.

Go adds to the response:

- `priority_model`: full persisted metadata;
- `task_priorities`: all prediction records;
- `priority_source` and `priority_model_version` on each benchmark plan, or on the one-plan response;
- `dataset_id` provenance.

The request context timeout covers both Python inference and C++ execution. ML inference time is not included in C++ `preprocessing_ms`, `algorithm_ms`, or `total_runtime_ms`.

## 11. C++ integration

`Task.priority_score` is populated by `load_priorities` before solving.

Its effects are:

- Independent: descending task order.
- Greedy: descending order plus `wP × priority-delay` candidate cost.
- CP-SAT: `wP × priority-delay` objective term; Greedy priority ordering also affects warm-start hints.

Priority delay is:

```text
round(priority_score)
× ceil(max(0,start_slot-earliest_slot)/96)
```

Summed over tasks, it appears as `metrics.priority_weighted_delay`. `config/optimizer.conf` sets `wP=1`.

Every task remains compulsory. The model affects when a task is placed, not whether it is scheduled.

`frontend/app/page.tsx` defines `PriorityModel`, `TaskPriority`, and `priorityFor`.


## 14. Reproducibility and artifact compatibility

Reproducibility controls include:

- fixed NumPy seed 26027;
- fixed split seed 26027;
- fixed regressor seed 26027;
- pinned NumPy/scikit-learn/joblib versions;
- persisted resolved hyperparameters and scikit-learn version;
- stable feature-name order check.

The training timestamp changes on retraining, and binary joblib compatibility across scikit-learn versions is not guaranteed. Use `ml/requirements.txt` and keep the artifact and metadata together.

The implementation checks feature names but does not currently verify a cryptographic artifact checksum, metadata/model version match inside the binary, dependency version match before deserialization, or prediction count against tasks until C++ priority loading. Production hardening should add those controls.

## 15. Limitations and production path

Current limitations:

- synthetic policy labels rather than historical decisions/outcomes;
- only four features;
- current runtime overdue feature is zero for generated scenarios;
- no calibration analysis or uncertainty estimate;
- no subgroup/route/department error analysis;
- no drift detection or monitoring;
- no explainability beyond feature definitions and global bootstrap policy;
- no online learning;
- joblib artifacts require trusted provenance because pickle-based loading is unsafe for untrusted files.

A railway pilot should define the prediction target with domain experts, build time-consistent training examples, avoid future-information leakage, create train/validation/test splits by time or geography, compare against the explicit policy baseline, measure operational downstream effects, calibrate score meaning, audit errors, version data/model/code together, and retain the C++ validator as a non-ML safety boundary.

## 16. Viva answers

- **Why Gradient Boosting?** It handles nonlinear interactions on small tabular feature sets, is fast for batch inference, and needs little preprocessing. In v1 it demonstrates a replaceable learned priority boundary.
- **Why not let ML create the schedule?** Scheduling has exact combinatorial and safety constraints. ML supplies a preference score; CP-SAT/heuristics enforce feasibility and coordinate blocks.
- **Why are the metrics so high?** The labels are deterministic synthetic policy outputs, so the model is approximating a known formula. They are not claims about real-world railway accuracy.
- **Do all algorithms use identical priorities?** Yes. Go performs one batch per request and passes one temporary score file to a benchmark process that runs all three algorithms.
- **Can ML make a plan invalid?** A score can influence timing preferences, but hard constraints and independent validation do not depend on the score.
- **What changes with real data?** Training examples, target definition, feature adapter, artifact, and monitoring. The runtime interface can remain task features → versioned priority score → optimizer.
